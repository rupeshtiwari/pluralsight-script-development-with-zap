## 2. How Many Times Should You Clone?

<table>
<tr><td width="15%" align="center"><b>Recommended</b></td><td><b>One clone per recorder per course</b><p>Record three demos sequentially by switching branches inside one folder. Your repository source changes with the branch; the directory name stays the same. Prepare and clean up each demo before switching.</p></td></tr>
<tr><td align="center"><b>Team of 5</b></td><td>Each engineer has their <b>own</b> checkout on their own machine. They can record in parallel without relying on one another's local ZAP data.</td></tr>
<tr><td align="center"><b>Optional</b></td><td>Use <code>git worktree</code> to keep multiple branches available in separate local folders at once. This is useful for simultaneous code inspection, but <b>not necessary</b> for sequential recording. Parallel Docker stacks also require separate ports/project names.</td></tr>
</table>

<details open><summary><b><font color="#0284c7">A. First Time Only — One Git Clone</font></b></summary>

At your Mac's terminal, run these commands once:

```bash
cd ~
git clone https://github.com/rupeshtiwari/pluralsight-script-development-with-zap.git
cd pluralsight-script-development-with-zap
./setup/setup-macos.sh
git fetch origin
```

**Folder name:** A clone without a destination creates `~/pluralsight-script-development-with-zap`. Running the same clone command again does not create a new branch folder; it would fail because the folder already exists. You may instead supply an explicit destination such as `~/recording-zap` **once**, if that name is easier for the engineer.

Your normal recording checkout path is `~/pluralsight-script-development-with-zap`.

</details>

<details open><summary><b><font color="#9333ea">B. First: Validate the Completed Reference and Generate Narration Logs</font></b></summary>

**Example: Module 1 Demo 1** (replace the branch and folder using the direct playbook links above):

```bash
cd ~/pluralsight-script-development-with-zap
git status --short
git fetch origin
git switch m1-demo1-after
git rev-parse HEAD
cd demos/module1-demos/m1-demo1-targeted-injection-xss-csrf
./scripts/demo_reset.sh
./scripts/preflight_check.sh
ls -l logs/preflight-step-0[1-4].log
```

**Why:** The Narrator cannot wait for an entire demo recording. Preflight executes all four real concept-named steps on the completed reference, generating full and per-step transcripts from the same underlying script engine that the Recorder will execute. The untouched raw output is also retained under `logs/.producer/`.

Expected successful *summary*, not a manufactured live result:

```text
RESULT: 5 checks passed, 0 failed
REFERENCE: logs/preflight-step-01.log through logs/preflight-step-04.log
```

**Do not approve narration unless this run actually exited zero and produced all four logs.** Inspect any separate ZAP GUI or CI proof as well; the preflight transcript cannot magically capture a Script Console pane or GitHub Actions report.

Before switching branches:

```bash
mkdir -p ~/zap-production-evidence/m1-demo1
cp logs/preflight-step-0[1-4].log ~/zap-production-evidence/m1-demo1/
./scripts/demo_down.sh
cd ~/pluralsight-script-development-with-zap
git status --short
```

The copy preserves narrator-approved references independently of branch switching, cleanup and reset. **Never run `git clean -fdx` over your evidence.**

</details>

<details open><summary><b><font color="#0284c7">C. Switch To the Same Demo's Starter and Record</font></b></summary>

```bash
cd ~/pluralsight-script-development-with-zap
git switch m1-demo1-before
git rev-parse HEAD
cd demos/module1-demos/m1-demo1-targeted-injection-xss-csrf
cp ~/zap-production-evidence/m1-demo1/preflight-step-0[1-4].log logs/
./scripts/demo_reset.sh

# Set recording comparison mode OFF CAMERA
export DEMO_SYNC_MODE=1
export DEMO_SYNC_PHASE=compare

# Exact step commands for this demo
./steps/01-run-targeted-injection-scan.sh
./steps/02-verify-reflected-xss-contexts.sh
./steps/03-test-cross-session-csrf-token.sh
./steps/04-reconcile-security-alerts.sh

./scripts/demo_down.sh
```

**Read the [M1 Demo 1 Recorder/Narrator/Editor playbook](m1-demo1.md) first.** Step source, screen focus, visual evidence, actual values, and edit points are described there.

For script-authoring demos, the `*-before` branch intentionally does not contain the completed JavaScript, Python script, or YAML plan. **Author that code first**, following its learner guide, then record the resulting four checks. Do not claim a starter checkout will pass before the student work is done.

The per-step recorded output must match the approved normalized preflight reference. A mismatch is a **STOP/retake** until investigated; you may not substitute a historic PASS screenshot or hide a failing command.

</details>

<details><summary><b><font color="#16a34a">D. Move To a Second or Third Demo on the Same Mac</font></b></summary>

```bash
# After the previous demo's ./scripts/demo_down.sh:
cd ~/pluralsight-script-development-with-zap
git status --short
git fetch origin
git switch m1-demo2-after
cd demos/module1-demos/m1-demo2-javascript-http-sender
./scripts/demo_up.sh
./scripts/preflight_check.sh
```

Then save `m1-demo2` references, stop its stack, switch to `m1-demo2-before`, create the missing JavaScript exercise source, and record the four named commands in [M1 Demo 2's playbook](m1-demo2.md). Repeat this same pattern for whichever demo is assigned next.

**Uncommitted changes:** `git switch` can refuse when the new branch would overwrite source edits. Stop, preserve the intended recorded source in a reviewable commit on an appropriate work branch or copy it to a safe backup directory; do not force checkout or throw away work. You can use a separate worktree instead if you need both branches open at once.

**Ignored log files** may survive branch switches, but use the external evidence directory above as the definitive narrator handoff.

</details>

## 3. Producer Handoff — Who Does What?

<table>
<tr><td width="17%" align="center"><img src="https://img.shields.io/badge/RECORDER-Blue-0284c7"/></td><td><b>Exact footage.</b> Full-screen, readable terminal or VS Code / ZAP GUI. Show the exact named command for ~8 seconds before Enter. Show each actual output value for 6–8 seconds; one focus only. Give important buttons 8-second pre-click and 8-second post-click handles in raw footage. Record exact branch SHA, pane, URL, mouse target and scan/alert state.</td></tr>
<tr><td align="center"><img src="https://img.shields.io/badge/NARRATOR-Purple-9333ea"/></td><td><b>Natural ElevenLabs speech.</b> Use real per-step preflight references plus the corresponding filmed GUI/CI evidence. Teach one unique mechanism, parameter and operator decision per step. Copy the approved spoken lines from that demo's playbook and revise only against actual evidence; never voice invented numbers.</td></tr>
<tr><td align="center"><img src="https://img.shields.io/badge/EDITOR-Green-16a34a"/></td><td><b>Evidence-driven Camtasia cuts.</b> Cut on pane changes, before/after visible script typing, and after the output has been held legibly. One short square/arrow/callout per output focus, removed immediately on the next focus. Trim scanner waits and click handles. Match audio to the actual same-step output, not a different take.</td></tr>
</table>

## 4. Output Files and Approval

| Evidence artifact | Where to get it | How it is used |
|---|---|---|
| Full preflight log | `<demo>/logs/preflight-<timestamp>.log` | Full four-step validation context |
| Approved step baselines | `<demo>/logs/preflight-step-01.log` … `04.log` | Narrator begins in parallel |
| Filmed normalized step output | `<demo>/logs/recorded-step-01.log` … `04.log` | Terminal/audio parity |
| Untouched raw output and mismatch diff | `<demo>/logs/.producer/` | Detect hidden failures and variable values |
| Actual GUI / hosted CI evidence | ZAP Webswing / current GitHub Actions run | Claims preflight alone cannot observe |
| Video/audio edit manifest | Editor's private project folder | Per-line timecodes, callouts, source SHA |
